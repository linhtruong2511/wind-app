# Repository Guidelines

## Project Structure & Module Organization

This is a Python/Django GeoNode application. Core platform code is under `geonode/`; project-specific WIND functionality is in `apps/`, including models, serializers, services, migrations, templates, and tests. Frontend integration lives in `frontend/`. Deployment and service configuration are in `docker/`, `Dockerfile`, and `docker-compose.yml`; documentation is in `docs/` and top-level Markdown files. Prefer placing new tests next to the app they cover.

## Build, Test, and Development Commands

Use Docker Compose for a complete local environment:

- `docker compose build` builds the Django and Celery images.
- `docker compose up` starts services; `docker compose down` stops them.
- `bash test.sh <test labels>` runs Django tests with coverage inside the configured environment, e.g. `bash test.sh co2_management.tests`.

For formatting checks, run `flake8 geonode` and `black --check geonode`. Use the project's Python environment and `.env_dev`/`.env_test` settings rather than committing local secrets.

## Coding Style & Naming Conventions

Follow PEP 8 with four-space indentation. Use `snake_case` for Python modules, functions, and variables; `PascalCase` for classes and Django models; and descriptive lowercase template paths. Black is configured for a 120-character line length. Keep migrations generated by Django and do not manually reformat migration files.

## Testing Guidelines

Tests use Django's test runner, with pytest/pytest-django also available. Test files follow `tests.py`, `test_*.py`, or `*_tests.py`; test names should describe behavior, such as `test_import_quality_flags`. Add or update focused tests for every behavior change, then run the narrow app suite before the broader `make test` suite.

## Commit & Pull Request Guidelines

Use concise, imperative commit subjects that explain the change; recent history uses prefixes such as `feat:`, `upd:`, and `add`. Link commits and PRs to a GitHub issue when applicable. PRs should describe the goal, include relevant tests, complete the repository checklist, and add screenshots for UI changes. Keep bug fixes and small features focused, add tests unless there is a clear reason not to, and ensure Flake8/Black and CI pass.

## Security & Configuration

Never commit credentials or edits to local `.env` files. Use `.env.sample` as the reference for configuration, and report vulnerabilities according to `SECURITY.md`.

## Rules
1. DO NOT modify the code unless the user's request explicitly instructs you to modify or add code.
2. Prioritize suggesting possible solutions and approaches, then ask the user whether they want you to modify the code. ONLY begin making code changes after the user agrees
3. DO NOT use python command in local machine and ALWAY working with python in docker container (ex: `docker compose exec django ...`, `docker compose exec celery ...`) in this project.
